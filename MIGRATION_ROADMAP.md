# Migration to the high-level PyTango API — battle plan

## Context

`LimaCCDs.py` and the plugin servers here use the historical low-level PyTango API
(`PyTango.LatestDeviceImpl`/`Device_4Impl`, `PyTango.DeviceClass` with raw `attr_list`/`cmd_list`/
`device_property_list` dicts, `read_X`/`write_X`/`is_X_allowed` naming convention, `PyTango.Util`
bootstrap). Goal: rewrite to the high-level API (`tango.server.Device`, `@attribute`, `@command`,
`device_property`, `run()`).

## Constraints

1. **Scope = the whole ecosystem.** `lima` is a superproject with ~50 camera submodules under
   `camera/*`, each with its own Tango device following the same low-level contract. `AttrHelper` and
   `get_tango_specific_class_n_device()` are public contracts spanning all of them, not internal to this
   repo.
2. **Strict Tango compatibility** throughout — no observable interface change for existing clients
   (BLISS, GUIs, spec) at any step.
3. Migrating all ~50 camera repos is an ongoing effort, not a fixed-date deliverable, once the pattern
   and tooling exist.

## Safety net

The BLISS test suite (`bliss.git/tests/`, via `lima_simulator_context`) already runs a real `LimaCCDs` +
`Simulator` server and exercises it end to end — no need to build a characterization harness. It's the
regression gate for every migration step. Working baseline confirmed on this machine:
`test_lima_simulator.py` (41 tests) + 20 other files (354 tests). `test_autofilter`, `test_nxw_*`
(except `test_nxw_nowriter`), and `test_lima_scans` are excluded — they fail/hang even against the
current unmodified server, for reasons unrelated to `LimaCCDs` (missing env deps / BLISS session
plumbing). See git history of this file for the exact run recipe if it needs reproducing.

## Mapping guide (from the Mask.py + Simulator.py pilots)

- `device_property_list`→`device_property`, `attr_list`→`@attribute`, `cmd_list`→`@command`,
  `read_X`/`write_X`→`fget=`/setter, `is_X_allowed`→ same-name method (naming convention still works).
- Don't inherit the old `BasePostProcess` (still low-level). Reimplement its small bit (RunLevel,
  Start/Stop, init state) directly; only worth a shared high-level base once 2+ plugins are migrated.
- **Gotcha**: the legacy `__getattr__` catch-all (`BasePostProcess.__global_allowed`) only ever gated
  *attributes* in practice — old PyTango never resolved it for *commands* (no real `is_X_allowed` method
  exists on the class, so commands were always allowed). Don't blindly add `state==ON` guards to
  commands when porting; verify empirically what the original actually enforced.
- **Gotcha**: a method decorated with `core.DEB_MEMBER_FUNCT`/`DEB_GLOBAL_FUNCT` must not use bare
  `super()` — it rebuilds the function object and chokes on the implicit `__class__` closure cell. Call
  the parent class by name instead (`Device.init_device(self)`).
- **Testing gotcha**: to test a local change against the real env, swap the one changed file in
  site-packages (backup, copy, restore) rather than pointing `PYTHONPATH` at the whole checkout —
  otherwise `lima.server.camera` (regular package) resolves entirely to the local tree, hiding
  camera plugins that ship as bare files in the env's site-packages (e.g. `Simulator.py`).
- **`AttrHelper.make_fget_fset(attr_name, *interfaces, enum=None)`**: the high-level replacement for the
  `get_attr_4u` naming-convention dispatch (`interfaces` are `f(self) -> target` callables, tried in
  order). Several attributes share their name with a `device_property` of the same name (the property is
  only the initial hardware config, consulted once in `init_device`) — `device_property` has no `name=`
  override, but `attribute(name=..., fget=, fset=)` does, so bind the property to the plain identifier
  and the attribute to a differently-named one (`mode`/`mode_attr`).
- Found bugs while porting are very likely pre-existing, not migration regressions - verify against the
  original before "fixing" anything (see the 3 Simulator.py bugs above, and Mask's Start/Stop in Phase 1).

## Decisions made

- Scope: whole ecosystem, not just this repo.
- Strict Tango compatibility required throughout.
